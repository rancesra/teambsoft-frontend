Es decir que hoy un administrador no tiene forma de ver los productos que desactivó: desaparecen de su vista y solo se llega a ellos si alguien guardó el id. 3.2 Confirmar antes de desactivar

¿Desactivar “Camiseta básica algodón”?

Dejará de aparecer en el listado público y en la tienda.

No se puede deshacer desde la aplicación.

El otro hueco del contrato: hoy no hay manera de volver a activar un producto. DELETE pone activo:false y PUT ignora el campo activo a propósito (§2), así que no existe el camino de vuelta. Por eso el diálogo dice que no se puede deshacer: sería mentir si dijera otra cosa. Habría que decidir en equipo si se agrega esa operación al contrato o si se deja así a propósito.

Contrato §3: las reglas del formulario son exactamente las del modelo: nombre obligatorio de máximo 120 caracteres, precio mayor que 0, stock 0 o más, categoría que exista en GET /categorias; descripción e imágenes opcionales. La validación del navegador solo sirve para avisar rápido: la que manda es la del backend.
Historia 4: “actualizarlo no cambia su estado: si estaba inactivo, sigue inactivo”. O sea que el formulario también se abre sobre un producto desactivado, y en ese caso tiene que avisarlo —igual que el detalle— para que nadie crea que al guardar lo está volviendo a publicar. Guardar no lo reactiva.
Contrato §2: PUT reemplaza el producto completo. Al editar, el formulario carga todos los campos y los envía todos: si se omite la descripción, esa descripción se borra. id y activo se ignoran aunque se envíen.

3.4 Cuando la operación sale bien

Creado · 201

Producto creado. Ya aparece en el catálogo.
POST devuelve el producto con su id asignado, así que desde aquí se puede ir directo a su detalle.

Actualizado · 200

Cambios guardados.
PUT devuelve el producto ya actualizado: la vista se refresca con esa respuesta, sin volver a pedirlo.

Desactivado · 204

Producto desactivado.
204 viene sin cuerpo: no hay datos que mostrar, solo confirmar y volver al listado.
Contrato §2: “Desactivar” llama a DELETE, que responde 204 sin cuerpo y es idempotente: repetirlo no es un error ni vuelve a publicar el evento. Debe pedir confirmación, porque el producto desaparece del listado público.

4. Estados que toda vista debe tener

No son adornos: cada uno corresponde a una respuesta que el backend puede dar hoy.

Cargando

Mientras la llamada está en curso. Nunca una pantalla en blanco.

Una categoría sin productos responde 200 con total: 0, no un error.

Contrato §4: todos los errores llegan como { "codigo": "...", "mensaje": "..." }. Los códigos de esta entrega son PRODUCTO_NO_ENCONTRADO (404) y VALIDACION_FALLIDA (400). Cualquier otra cosa se trata como error inesperado.

5. Mapa de rutas

Lo que F1 necesita para configurar el enrutador, y lo que hay que reservar en el Host App para que las rutas de los tres módulos no choquen.

RutaVistaQué llama
/catalogoListado públicoGET /productos + GET /categorias
/catalogo/:idDetalleGET /productos/{id}
/catalogo/adminListado de administraciónGET /productos
/catalogo/admin/nuevoCrearGET /categorias + POST /productos
/catalogo/admin/:idEditarGET /productos/{id} + PUT /productos/{id}
El filtro y la página van en la URL (/catalogo?categoria=cat-ropa&pagina=2). Así, recargar la página o compartir el enlace conserva lo que el usuario estaba viendo, en vez de devolverlo a la página 1.
Contrato §2: POST, PUT y DELETE están marcados como Admin, pero Keycloak no se integra en esta entrega y los endpoints todavía no validan token. En la práctica: las rutas /catalogo/admin/* no se enlazan desde la navegación pública, y cuando entre Keycloak se les pone el guardia de verdad. Conviene decirlo en la sustentación antes de que lo pregunten.

8. Lo que hay que acordar entre los 3 equipos

Esto es lo que el mockup deja abierto a propósito. El contrato §9 ya dice que el mecanismo de integración está pendiente de decidir; el resto son consecuencias de esa misma decisión.

  1. Mecanismo de integración. Cómo carga el Host App cada módulo: Module Federation (los 3 usamos Vue, así que el módulo se carga en caliente y comparte enrutador), componentes web (más aislado, funciona incluso con frameworks distintos) o composición por rutas (lo más simple: cada módulo es su propia página). Nuestra propuesta: Module Federation, porque ya acordamos Vue para los 3 y es lo que se entiende por microfrontend; el costo es que los 3 tenemos que usar la misma versión de Vue y alinear la configuración de build.
  2. Quién es dueño del Host App y mantiene el encabezado, la navegación y las rutas.
  3. Espacio de nombres de rutas. Proponemos que todo lo nuestro cuelgue de /catalogo/*, para que las rutas de los tres módulos no choquen.
  4. Estilo compartido. Si cada equipo elige sus colores, el Host App se ve como tres páginas pegadas. Lo más barato es acordar media docena de variables CSS (color de acento, texto, borde, fondo, radio y tipografía) en vez de una librería de componentes: una librería pesada, repetida en tres módulos, tiene que declararse como dependencia compartida o se descarga tres veces. En este mockup ya hay una paleta que podemos proponer.
  5. El botón “Agregar al carro”: ¿lo pinta Catálogo y emite un evento, o lo inyecta el Host App en un espacio nuestro?
  6. Estado compartido: sesión del usuario y contador del carro. Qué módulo lo guarda y cómo se entera el resto.
  7. Kong: el base path de cada módulo y la configuración de CORS. Para desarrollo proponemos el proxy de Vite; en integración, el plugin de CORS de Kong, y no configurarlo también en Spring, porque las cabeceras se duplican y el navegador rechaza la respuesta.
Ojo con el contrato: nada de esto cambia el contrato de servicio v2.2 — endpoints, modelos y eventos quedan igual, así que los equipos A y C no tienen que tocar su integración por REST. Lo que se acuerde aquí actualiza la sección §9 del contrato, y eso se hace después de la reunión, con su cambio de versión y su fila en el historial.
